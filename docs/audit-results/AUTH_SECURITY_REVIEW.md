# Auth Security Review

**Last audited:** 2026-07-27

## Summary

DevDrop's custom auth layer (registration, credentials sign-in, email verification, password reset, change-password, delete-account) is well-built overall: bcrypt is used correctly throughout, tokens are generated with `crypto.randomBytes(32)` (256 bits of CSPRNG entropy), password-reset and email-verification tokens are namespaced to prevent cross-use, tokens are deleted on consumption, and every mutating profile route validates the session server-side and operates only on `session.user.id`. No critical vulnerabilities were found. The most significant gap is the complete absence of rate limiting / brute-force protection across all auth endpoints (registration, sign-in, forgot-password, resend-verification, reset-password), which is realistic to flag given this is pre-launch but still worth prioritizing before launch. A handful of lower-severity items (timing side channel in `forgot-password`, JWT session persistence after password change/account deletion, minor consistency issues) round out the findings.

**Findings by severity:** 0 Critical, 1 High, 2 Medium, 3 Low.

## Findings

### 🔴 Critical
None found.

### 🟠 High

#### No rate limiting or brute-force protection on any auth endpoint
- **File:** `src/auth.ts:1-80` (Credentials `authorize()`), `src/app/api/auth/register/route.ts`, `src/app/api/auth/forgot-password/route.ts`, `src/app/api/auth/resend-verification/route.ts`, `src/app/api/auth/reset-password/route.ts`
- **Issue:** None of the custom auth routes implement any form of rate limiting, IP throttling, or attempt tracking. This is an absence, not a bug in existing logic — confirmed via repo-wide search (`rate.?limit|ratelimit|Ratelimit` returns zero matches in `src/`) and by reading each route in full. NextAuth v5 does not provide this for the Credentials provider; it is entirely the app's responsibility.
- **Exploit scenario:** An attacker can script unlimited password-guessing attempts against `POST /api/auth/register` and NextAuth's credentials sign-in (unlimited login attempts per account = classic credential-stuffing/brute-force target), spam `POST /api/auth/forgot-password` and `POST /api/auth/resend-verification` to flood a victim's inbox or exhaust the Resend send quota, and hammer `POST /api/auth/reset-password` to brute-force a reset token (though the token itself is a 256-bit random hex string, so brute-forcing it directly is not practically feasible — see Passed Checks — the bigger risk is abuse volume/cost and account-guessing on sign-in).
- **Fix:** Add a rate limiter (e.g., Upstash `@upstash/ratelimit` with Redis, or an in-memory/IP+email composite limiter for a single-instance deployment) in front of: credentials `authorize()` (limit by email+IP, e.g., 5 attempts / 15 min), `register` (limit by IP, e.g., 5/hour), `forgot-password` and `resend-verification` (limit by email and IP, e.g., 3/hour), and `reset-password` (limit by IP). Given this is pre-launch with no evidence of active exploitation, this is realistically High rather than Critical, but should be resolved before public launch.

### 🟡 Medium

#### JWT sessions remain valid after password change or account deletion mid-session
- **File:** `src/app/api/auth/change-password/route.ts` (full file), `src/app/api/auth/reset-password/route.ts` (full file), `src/auth.ts:22` (`session: { strategy: "jwt" }`)
- **Issue:** DevDrop uses NextAuth's JWT session strategy (confirmed in `src/auth.ts:22`). Changing a password via `change-password` or `reset-password` updates the `User.password` hash in the database but does not invalidate any JWT session cookies already issued to that user (on the same device or others). Since JWT sessions are stateless and not looked up against the DB per-request by default, a session obtained before the password change continues to work until it naturally expires.
- **Exploit scenario:** If an attacker has already compromised a victim's session cookie (e.g., via a stolen device, XSS elsewhere, or a shared/public computer), the victim changing their password via "Change Password" or completing a "Forgot Password" reset (intended to lock the attacker out) will **not** revoke the attacker's already-issued session — the attacker retains access until the JWT naturally expires.
- **Fix:** This is a known, documented tradeoff of NextAuth's JWT strategy (not a NextAuth defect) and is acceptable to leave as-is for now, but should be a deliberate, tracked decision. If stronger guarantees are wanted later: (a) switch to the database session strategy so sessions can be revoked via `prisma.session.deleteMany({ where: { userId } })` on password change/reset, or (b) add a `passwordChangedAt` timestamp to `User` and check it against the JWT's `iat` claim in the `jwt`/`session` callbacks in `src/auth.ts`, rejecting stale tokens. Flagging at Medium because it's a deliberate architectural gap worth a conscious decision, not an active exploit.

#### `resend-verification` and `forgot-password` do not enforce a cooldown between requests
- **File:** `src/app/api/auth/resend-verification/route.ts:31-38`, `src/app/api/auth/forgot-password/route.ts:26-31`, `src/lib/verification-token.ts:7-8,33-35`
- **Issue:** Each call to these endpoints (when the account exists, has a password, and — for resend — is unverified) immediately generates a brand-new token via `createVerificationToken`/`createPasswordResetToken`, which first runs `prisma.verificationToken.deleteMany({ where: { identifier } })` before creating the new one — deleting any prior still-valid, unconsumed token. No minimum interval is enforced between requests. Combined with the missing rate limiting (see High finding above), a single actor can trigger unlimited emails to a target address.
- **Exploit scenario:** Repeatedly calling `POST /api/auth/forgot-password` or `POST /api/auth/resend-verification` with a known victim email floods their inbox with reset/verification links (annoyance/spam vector) and burns through the Resend sending quota; each new token issuance also invalidates the user's *own* legitimately-requested still-valid token (self-inflicted DoS on the real user if an attacker keeps re-triggering it while the victim is mid-flow, since only the newest token is valid).
- **Fix:** This overlaps with the rate-limiting finding above and can be resolved by the same fix (per-email cooldown, e.g., reject a new token request within 60s of the last one for that identifier by checking `VerificationToken.expires` against `now + TOKEN_TTL_MS - 60s`). Noted separately here because it's specifically about email-bombing/quota-exhaustion and self-inflicted token invalidation rather than credential brute-forcing.

### 🟢 Low

#### `forgot-password` response is generic but timing may still differ between existing/non-existing accounts
- **File:** `src/app/api/auth/forgot-password/route.ts:26-33`
- **Issue:** The route correctly returns the same generic JSON success response regardless of whether the account exists or has a password (confirmed by reading the full route — the `if (user?.password)` branch and the fallthrough both return `NextResponse.json({ success: true })`). However, the code path that finds a user with a password and sends an email (DB lookup + token creation, including a `deleteMany` + `create` round trip + a synchronous `await resend.emails.send(...)` Resend API call) takes measurably longer than the path that finds no user or a passwordless user (single DB lookup, no further work). This is a response-timing side channel, not a response-content one.
- **Exploit scenario:** An attacker measuring response latency at scale could statistically distinguish "account exists with a password" from "account doesn't exist / is GitHub-only" even though the JSON body is identical, enabling user enumeration.
- **Fix:** Low priority given this requires statistical timing analysis and DevDrop is pre-launch, but if it's ever hardened: pad the fast path to match the slow path's typical latency, e.g. `await Promise.all([workPromise, new Promise(r => setTimeout(r, 300))])` around the whole conditional block, or move the email send to a fire-and-forget/background call so both paths return in similar time.

#### Password reset does not send a confirmation notification email
- **File:** `src/app/api/auth/reset-password/route.ts:40-45`
- **Issue:** After a successful password reset (`prisma.user.update` with the new hash), no email is sent to notify the account owner that their password was changed. Not a vulnerability in the strict sense — but if an attacker did successfully reset a password via a leaked/guessed token or compromised email inbox, the legitimate owner has no out-of-band signal that it happened.
- **Exploit scenario:** N/A directly — this is a defense-in-depth/detection gap rather than an exploitable flaw. Noted for completeness since it affects how quickly a real compromise would be noticed.
- **Fix:** After successfully updating the password in `reset-password/route.ts`, fire-and-forget a "your password was changed" notification email (mirroring the existing pattern in `send-password-reset-email.ts`), wrapped in a try/catch-and-ignore like the one already used for verification emails in `register/route.ts:54-60`, so a delivery failure doesn't block the response.

#### `delete-account` has no secondary server-side proof of intent beyond the session
- **File:** `src/app/api/auth/delete-account/route.ts:5-17`, `src/components/profile/DeleteAccountDialog.tsx:21-40`
- **Issue:** The route correctly calls `auth()` before any Prisma access and correctly scopes deletion to `session.user.id`. However, unlike `change-password` (which requires and bcrypt-verifies the current password), `delete-account` requires no secondary proof of intent server-side — the only confirmation is the client-side "type DELETE" text field in `DeleteAccountDialog.tsx`, which is a UI-only gate with no corresponding server check.
- **Exploit scenario:** If an attacker obtains a valid session token (e.g., via a stolen device left logged in, or a leaked cookie from another vulnerability), they can immediately and irreversibly delete the account with a single `DELETE /api/auth/delete-account` request — no password re-entry required. This is a lower-severity, defense-in-depth concern rather than a direct vulnerability since it requires session compromise as a prerequisite, and the client-side friction (typing "DELETE") does not stop a scripted request directly against the API.
- **Fix:** Consider requiring current-password re-entry (server-side verified via bcrypt, like `change-password` already does) before deletion for accounts with a password set, falling back to a different confirmation (e.g., re-typing the account's email, verified server-side against `session.user.email`) for GitHub-only accounts with no password. This is a reasonable pre-launch backlog item rather than an urgent fix.

## Passed Checks

- **Password hashing (registration):** `bcrypt.hash(password, 12)` in `src/app/api/auth/register/route.ts:43` — cost factor 12 is within OWASP's recommended range (10-12) and appropriate for a Node.js API route.
- **Password hashing (reset):** `src/app/api/auth/reset-password/route.ts:40` uses `bcrypt.hash(password, 12)` when writing the new password, consistent with registration.
- **Password hashing (change):** `src/app/api/auth/change-password/route.ts:58` uses `bcrypt.hash(newPassword, 12)`, and — critically — requires and verifies the *current* password via `bcrypt.compare(currentPassword, user.password)` at line 50 before allowing any change, rejecting with 400 at lines 51-56 if it doesn't match.
- **Password comparison (sign-in):** `src/auth.ts:55-58` uses `bcrypt.compare(parsed.data.password, user.password)` — never a plaintext or `===` comparison.
- **No plaintext logging/serialization of passwords:** `register/route.ts:63-66` only returns `{ id: user.id, name: user.name, email: user.email }` in its JSON response (the `password` field is never included, and the full `user` object created by `prisma.user.create` is never spread into the response); `change-password` and `delete-account` responses only return `{ success: true }`-style bodies with no user object; `src/lib/db/user.ts`'s `getUserProfile()` uses a Prisma `select` that only exposes `id, name, email, image, createdAt` plus a derived boolean `hasPassword` computed server-side from `!!user.password` (the hash itself never leaves the function).
- **GitHub-only accounts correctly rejected from credentials sign-in:** `src/auth.ts:53` checks `if (!user?.password) return null` before attempting any bcrypt comparison, preventing both a crash on `bcrypt.compare(password, null)` and any behavioral difference that could leak account-provider info via error type.
- **`change-password` rejects GitHub-only accounts server-side:** `src/app/api/auth/change-password/route.ts:43-48` checks `if (!user?.password)` and returns a 400 error before any update — not just a UI-hidden control. `ChangePasswordForm` in `src/components/profile/ChangePasswordForm.tsx` is additionally only rendered when `hasPassword` is true (`src/app/profile/page.tsx:68`), but the server-side check is the actual security boundary.
- **Cryptographically secure token generation:** `src/lib/verification-token.ts:10,37` uses `crypto.randomBytes(32).toString("hex")` for both email-verification and password-reset tokens — Node's `crypto.randomBytes` is backed by the platform CSPRNG and 32 bytes yields 256 bits of entropy, well above what's needed to resist brute-force/guessing; not `Math.random()` or any predictable source.
- **Token expiration enforced:** Both `createVerificationToken` and `createPasswordResetToken` in `src/lib/verification-token.ts` set `expires` to `Date.now() + TOKEN_TTL_MS` (24 hours, line 4), and both `consumeVerificationToken` (line 24) and `consumePasswordResetToken` (line 53) explicitly check `if (record.expires < new Date())` and delete+reject expired tokens before treating them as valid, rather than relying solely on a DB constraint.
- **Single-use tokens:** Both consume functions in `src/lib/verification-token.ts` (lines 29 and 58) delete the token record via `prisma.verificationToken.delete({ where: { token } })` immediately after successful validation, so a reused token (replay) fails cleanly with an `"invalid"` error on the second attempt in both `verify-email/route.ts` and `reset-password/route.ts`.
- **Token namespace isolation (`pwreset:` prefix):** `createPasswordResetToken`/`consumePasswordResetToken` in `src/lib/verification-token.ts:33-63` prefix the `identifier` field with `pwreset:` before writing/reading `VerificationToken` rows, while email-verification tokens use the bare email as `identifier` (lines 7-18). `consumePasswordResetToken` additionally re-checks `record.identifier.startsWith(PASSWORD_RESET_PREFIX)` at line 49 before accepting a token, and `consumeVerificationToken` looks up tokens purely by the unique `token` value and returns `record.identifier` directly as the email — since a password-reset token's stored identifier is always prefixed, it would incorrectly "verify" an email like `pwreset:user@example.com` rather than the real address, causing the update in `verify-email/route.ts:20-22` to silently fail to match any user rather than cross-contaminating a real account. Confirmed by reading both function bodies — the two token types cannot be used interchangeably by the wrong endpoint.
- **`forgot-password` avoids user enumeration via response content/status:** `src/app/api/auth/forgot-password/route.ts:26-33` returns the identical `{ success: true }` response (same 200 status) whether the account doesn't exist, exists but has no password (GitHub-only), or exists and an email is actually sent — verified by reading the full route. (See Low finding above for the separate, minor timing-based side channel.)
- **`resend-verification` avoids user enumeration:** `src/app/api/auth/resend-verification/route.ts:27-35` similarly returns a generic `{ success: true }` response regardless of account existence or verification state, and no-ops (still returning success) when `isEmailVerificationEnabled` is false (`src/lib/config.ts`).
- **Session validation before any DB mutation:** `change-password/route.ts:20-26` and `delete-account/route.ts:7-13` both call `const session = await auth()` and return 401 via `if (!session?.user)` as the very first statements in each handler, before any `prisma.*` call.
- **IDOR protection — operations scoped to session's own user id:** Both `change-password` (lines 40-41, 60-62) and `delete-account` (line 15) use `session.user.id` (never a client-supplied `userId`/`email` from the request body) in every Prisma `where` clause, confirmed by reading both handlers in full — there is no code path where a client-supplied identifier reaches a Prisma query.
- **`delete-account` uses schema-level cascade, not manual multi-step deletion:** `src/app/api/auth/delete-account/route.ts:15` performs a single `prisma.user.delete({ where: { id: session.user.id } })`; `prisma/schema.prisma` defines `onDelete: Cascade` on the `Item.user` (line 106), `Collection.user` (line 155), `ItemType.user` (line 132), `Account.user` (line 53), and `Session.user` (line 65) relations, so dependent rows are removed atomically by Postgres as part of the single delete rather than via separate application-level deletes that could partially fail.
- **No sensitive fields in JSON responses:** Verified across `register`, `verify-email` (redirect only, no JSON body), `resend-verification`, `forgot-password`, `reset-password`, `change-password`, and `delete-account` — none of these routes include `password`, raw verification/reset tokens, or other hash/secret material in their response bodies.
- **Email verification token check happens before consumption, not after:** `src/app/api/auth/verify-email/route.ts:14-23` calls `consumeVerificationToken`, which internally validates expiry (deleting and rejecting if expired) and existence, and only returns success with the associated email after those checks pass; the route then updates `emailVerified` only when `result.success` is true — there is no window where an expired/invalid token is treated as valid before being checked.

## Out of Scope (Handled by NextAuth)

The following were intentionally not audited, as NextAuth v5 (Auth.js) handles them correctly by default and no code in this project overrides or disables that behavior:

- CSRF protection on `/api/auth/*` routes (NextAuth's built-in CSRF token handling for its own endpoints).
- Session cookie flags (`httpOnly`, `secure`, `sameSite`) — default NextAuth JWT cookie configuration in `src/auth.ts` is unmodified.
- OAuth `state`/PKCE handling for the GitHub provider — standard `GitHub` provider configuration in `src/auth.config.ts`/`src/auth.ts` with no custom overrides.
- Session token signing under the JWT strategy — `src/auth.ts` uses NextAuth's default JWT encoding/signing with `AUTH_SECRET`, no custom `encode`/`decode`.
- Redirect URL validation for NextAuth's own callback flow (`/api/auth/callback/*`).
